# Valentine Express — Live. Gift. Connect.

Real-time live streaming platform with gifts, chat, creator wallets, and PayPal payouts.
Built with Next.js 16, Socket.IO, Prisma (Postgres / Neon), and WebRTC.

---

## Quick Start

```bash
# 1. Install dependencies
bun install

# 2. Copy .env.example to .env and fill in secrets (DATABASE_URL from Neon, Cloudinary keys, PayPal sandbox keys, BETTER_AUTH_SECRET)
cp .env.example .env

# 3. Sync the schema to your Neon Postgres database
bunx prisma db push
# (this diffs your live database against prisma/schema.prisma and applies
#  the difference — see the note below on why this project uses db push
#  instead of the migration-file-based `prisma migrate deploy`)

# 4. Start the WebSocket service (port 3001)
cd mini-services/ws-service && bun install && bun run dev &

# 5. Start the Next.js app (port 3000)
cd ../.. && bun run dev
```

Open the Preview Panel on the right → you'll see the Valentine Express landing page.

> **Schema sync on every deploy:** the `build` script in `package.json` runs
> `prisma db push --accept-data-loss` before `next build`, so Vercel
> automatically syncs your Neon database's actual columns/tables to match
> `prisma/schema.prisma` on every deploy — no need to run migration
> commands by hand from a terminal.
>
> This uses `db push` (diffs the live database and applies whatever's
> different) rather than `prisma migrate deploy` (replays a tracked history
> of migration files) because this project's migration files were
> hand-written to match the schema rather than generated by actually
> running `prisma migrate dev` against Neon — so there's no guarantee the
> migration history exactly matches what's live in your database, and
> `migrate deploy` would fail with "relation already exists" errors if it
> doesn't. `db push` sidesteps that by not caring about history, only the
> current diff.
>
> The tradeoff: `--accept-data-loss` means a schema change that *removes* a
> column/table would silently drop that data on the next deploy, with no
> confirmation prompt (there's no interactive terminal during a Vercel
> build). That's fine for the additive changes so far, but if you ever
> remove a field from the schema, deploy that change manually first
> (`bunx prisma db push` from your own machine, where you'll see the
> warning and can confirm) rather than letting it happen unattended in a
> build.
> `bunx prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --script`
> against your real DATABASE_URL to confirm there's no drift, or simply run
> `bunx prisma migrate dev` once against a fresh Neon database and let Prisma
> regenerate/verify it for you.

## Deploying (Vercel + separate WS host)

The Next.js app and the realtime WebSocket/WebRTC-signaling service
(`mini-services/ws-service`) are **two separate deployments** — Vercel's
serverless functions can't run a persistent Socket.IO server.

**1. Next.js app → Vercel**
- Push this repo to GitHub, import it in Vercel.
- Add all the secrets from `.env.example` in Vercel → Project → Settings →
  Environment Variables (`DATABASE_URL`, `BETTER_AUTH_SECRET`,
  `CLOUDINARY_*`, `PAYPAL_*`, `ADMIN_EMAILS`, etc.).
- Also set `NEXT_PUBLIC_WS_URL` to the public URL of your ws-service
  deployment (step 2) — `NEXT_PUBLIC_*` vars are baked in at build time, so
  set this *before* the first deploy/build.
- For Postgres on serverless, use Neon's **pooled** connection string
  (the "-pooler" endpoint, or append `?pgbouncer=true`) for `DATABASE_URL` —
  otherwise many concurrent Vercel function invocations can exhaust your
  database's connection limit.

**2. Realtime backend → pick ONE:**

**Option B (recommended if you don't want to give a host your card):
Cloudflare Worker** — see `mini-services/cloudflare-ws/README.md` for the
full walkthrough (`wrangler login` → `wrangler secret put` → `wrangler
deploy`). Cloudflare's free Workers/Durable Objects tier genuinely doesn't
require a credit card, unlike Railway/Render/Fly.io. This is a full
from-scratch rewrite of the realtime layer for Cloudflare's runtime (it
can't run Socket.IO) — same features, same database, different code path.

**Option A: `mini-services/ws-service` → Railway / Render / Fly.io / a VPS
(NOT Vercel)**
- Deploy `mini-services/ws-service` as its own Node process. It is fully
  self-contained (own `prisma/schema.prisma`, own copy of the gift catalog)
  so it works correctly even on hosts that only include the chosen Root
  Directory in the build context (e.g. Railway).
  - Root Directory: `mini-services/ws-service` (adjust if your repo has an
    extra wrapper folder around it — check your host's build logs to see
    the actual path it's building from)
  - Build Command: `bun install` (this also runs `prisma generate` via the
    package's `postinstall` script)
  - Start Command: `bun run start`
- Set `DATABASE_URL` (same Neon DB), `BETTER_AUTH_SECRET` (must match the
  Next.js app's value exactly — it verifies the same signed session tokens),
  and `FRONTEND_URL` (your Vercel domain, for CORS).
- The platform usually injects its own `PORT` — the service already reads
  `process.env.PORT`.

**Either way:** copy the public URL you get into the Next.js app's
`NEXT_PUBLIC_WS_URL` on Vercel and redeploy.

> **Maintenance note:** `mini-services/ws-service/prisma/schema.prisma` and
> `mini-services/ws-service/lib/gifts.ts` are duplicates of the main app's
> `prisma/schema.prisma` and `src/server/gifts.ts` — kept as local copies so
> ws-service deploys standalone. If you change the database schema or the
> gift catalog/pricing, update both copies.

Both deployments must share the same `BETTER_AUTH_SECRET` and the same
Postgres database, or logins/sessions won't work across the two.

## Free coins (daily bonus modal + rewarded ad grid)

Two ways for users to earn coins without paying:

- **Daily login bonus** — a modal pops up automatically on login/app open
  when a bonus is available (checked via `GET /api/wallet/daily-claim`,
  claimed via `POST` to the same route). Amount is
  `DAILY_LOGIN_BONUS_COINS`. Claiming within 24-48h of the last claim grows
  a visual streak (`Wallet.dailyStreak`); a longer gap resets it to 1.
  There's no button for this in the Wallet page anymore — it's fully
  popup-driven.
- **Watch ads for coins** — the Wallet page shows a grid of slots (default
  12, set by `AD_REWARD_DAILY_CAP`) instead of a single button. Each slot
  watch: `POST /api/wallet/ad-reward/start` issues a short-lived signed
  token, the ad plays, `POST /api/wallet/ad-reward/claim` credits
  `AD_REWARD_COINS` once the ad reports completion. `AD_REWARD_COOLDOWN_MINUTES`
  paces individual watches; the grid resets at UTC midnight.

**HilltopAds setup (Video VAST):** HilltopAds' Video VAST format returns a
standard VAST XML tag — this is a much better fit than their other formats,
since VAST is a documented protocol with a real "complete" tracking event
that fires only once the video actually finishes, rather than a proprietary
embed we'd have to guess at.

1. Create a Video VAST ad zone in your HilltopAds publisher dashboard and
   copy its VAST tag URL.
2. Set `NEXT_PUBLIC_HILLTOP_VAST_URL` to that URL.

That's it — `RewardedVastAd` in `src/app/page.tsx` fetches the tag, follows
one Wrapper redirect if HilltopAds returns one (common with ad networks
that resell inventory), plays the media file in a fullscreen modal, fires
the VAST `Impression` pixel on load and the `complete` tracking pixel when
the video ends, and only then calls the claim endpoint.

**Honest limitation:** the VAST `complete` event is a real signal from the
video element's own `ended` event — meaningfully stronger than a generic
"trust the client" callback. It still isn't a server-to-server guarantee
(a user could, in principle, tamper with the page's JS to fire `onEnded`
early). The token-based claim flow plus per-user cooldown keeps this to
"determined tampering only," not casual abuse. For a stronger guarantee,
you'd need HilltopAds' S2S postback wired to your specific ad zone.

> ⚠️ Note: the original spec for this project said to **disable free demo
> coin grants in production**. This feature reintroduces a (small, rate
> limited) source of free coins by design — make sure that's actually what
> you want before shipping it, since it changes the economics of the coin
> pack pricing.

## Cloudinary (KYC / avatar / status images)

Image uploads (avatar, KYC selfie + NIC front/back, status post images) go
**directly from the browser to Cloudinary** — not through our own server.
The flow: the browser compresses the image client-side (resized to a max
1600px edge, recompressed as JPEG), then calls `POST /api/uploads/sign`
(authenticated) to get a short-lived signature generated with your
`CLOUDINARY_API_SECRET`, then POSTs the file straight to Cloudinary's API
using that signature. The resulting `secure_url` is saved via the relevant
API (`/api/profile`, `/api/kyc/submit`, `/api/statuses`).

This two-step signed-direct-upload design exists specifically to avoid a
`413 Payload Too Large` error: routing image bytes through our own Vercel
serverless function hits Vercel's request body size limit on larger photos.
Uploading directly to Cloudinary sidesteps that limit entirely, regardless
of file size (up to Cloudinary's own limits).

1. Create a free [Cloudinary](https://cloudinary.com/) account
2. From the dashboard, copy **Cloud name**, **API Key**, **API Secret** into `.env`
3. No further setup needed — folders (`valentine-express/avatars/...`,
   `valentine-express/kyc/...`, `valentine-express/statuses/...`) are created
   automatically on first upload

**Privacy note:** KYC images currently use Cloudinary's standard delivery
(URL-accessible by anyone who has the link, though the per-user folder path
isn't guessable). For stricter access control before handling real user
documents at scale, switch KYC uploads to Cloudinary's "authenticated"
delivery type with signed, time-limited URLs — see the comment in
`src/server/cloudinary.ts`.

## Web Push Notifications (Firebase Cloud Messaging)

- **Setup:** Firebase Console → Project Settings → Cloud Messaging → Web
  Push certificates → generate/copy the VAPID key. Set
  `NEXT_PUBLIC_FIREBASE_VAPID_KEY` and the rest of the
  `NEXT_PUBLIC_FIREBASE_*` vars (API key, project id, etc. — same values
  used for `src/lib/firebase.ts`'s existing Analytics setup).
- **`public/firebase-messaging-sw.js`** has its own hardcoded copy of the
  Firebase config — service workers are static files and can't read
  `process.env`. If you change Firebase projects, update both places.
- **Enabling:** users opt in from Profile → Notifications → "Enable
  notifications" (`requestNotificationPermission()` in
  `src/lib/push-notifications.ts`). This must run from a click/tap — browsers
  can ignore permission prompts triggered without a user gesture, which is
  why it isn't auto-triggered on page load.
- **Sending:** the resulting FCM token is saved on `User.fcmToken` (latest
  device wins — one token per user, not per-device; extend to a separate
  table if you need multi-device support). Send pushes from your backend
  using the Firebase Admin SDK with that token — this repo only implements
  the client-side registration + receiving side, not a send-a-push API
  route, since you didn't specify what should trigger a push (new gift?
  new DM? admin broadcast?).
- **Receiving:** foreground messages (tab open) show as an in-app toast
  (top-right, auto-dismisses); background messages (tab closed/minimized)
  are handled by the service worker as native OS notifications.

## Home page

The Home tab shows every registered user as a card (`GET /api/users`, up to
200 most recent) with a green/gray online-presence dot computed against the
currently-connected socket users. Tapping a card:
- jumps straight into that person's live stream if they're currently live
  (cross-referenced against active `netState.lives`), or
- opens a lightweight public profile view (`GET /api/profile?userId=...`)
  with a "Message" button that opens a DM.

The Status/Updates feed (post + scrolling list, optionally with an image)
is embedded directly beneath the user grid on the same page — there's no
separate Status tab anymore.

## Payment Provider Architecture

```
src/server/payments/
  types.ts          → PaymentProviderAdapter interface
  paypal.ts         → PayPal implementation (Orders + Payouts)
  dialogGenie.ts    → Dialog Genie stub (throws until configured)
  index.ts          → Re-exports
```

Select provider via env vars:
```
PAYMENTS_BUY_PROVIDER=paypal       # or: dialog_genie
PAYMENTS_WITHDRAW_PROVIDER=paypal   # or: dialog_genie
```

## Adding Dialog Genie Later

Dialog Genie is a Sri Lankan mobile payment gateway. To enable it:

1. Set `PAYMENTS_BUY_PROVIDER=dialog_genie` and/or `PAYMENTS_WITHDRAW_PROVIDER=dialog_genie`
2. Fill in `DIALOG_GENIE_API_KEY`, `DIALOG_GENIE_API_SECRET`, `DIALOG_GENIE_MERCHANT_ID`, `DIALOG_GENIE_BASE_URL`, `DIALOG_GENIE_WEBHOOK_SECRET`
3. Implement the methods in `src/server/payments/dialogGenie.ts` (follows the same interface as PayPal)
4. The same `coin_orders` and `cashout_requests` tables work — they store the `provider` column
5. No wallet logic needs to change — only the provider adapter
